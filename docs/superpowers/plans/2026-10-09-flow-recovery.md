# 流光溢彩与连接恢复实现计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 修正板端动画生命周期和流光溢彩效果，并让客户端在维护模式后可恢复连接、主动同步板端颜色与状态。

**Architecture:** 保持现有 UDP/CRC4 协议和 `0x05` 8 字节 payload 不变。板端把扫描线和彩虹渐变拆为两个明确方法，并用动画代次令旧线程失效；客户端把恢复连接作为显式 UI 操作，成功后主动执行 FD 同步。状态名称从“彩虹跑马”迁移为“流光溢彩”，保留旧本地状态兼容。

**Tech Stack:** MicroPython board runtime, Python 3 client, UDP, pywebview bridge, JSON UI persistence, unittest, Node `--check`.

**Spec:** `docs/superpowers/specs/2026-10-09-flow-recovery-design.md`

## Global Constraints

- `0x05` remains the externally mapped flow-color command with its existing 8-byte payload.
- `scan_line_x(..., rainbow=False)` remains board-internal and is not added to the external effect map.
- The flow-color effect is named `rainbow` in both board and client controller APIs.
- Rainbow mode does not consume client palette colors; colors are generated by firmware.
- A successful maintenance-mode recovery must restart health monitoring only after connect and sync complete.
- Failed sync preserves transport connectivity and leaves the current UI usable.
- This workspace has no Git repository; tests, compile checks, and the SDD ledger replace commits.

## Review Focus

- An old animation thread waking after `stop()` must not write a frame after a new effect starts; Task 1 tests generation invalidation.
- `rainbow()` must write every cell in the configured range in each frame, while `scan_line_x(rainbow=False)` must use the supplied RGB value; Task 1 tests the effect contract.
- A fresh FF handshake after maintenance must issue FD sync and apply a board-reported static RGB color; Task 3 tests the recovery decision path and Bridge mapping.
- An old persisted “彩虹跑马” state must load as “流光溢彩” without losing its palette; Task 3 tests migration.
- Sync failure after reconnect must not start health polling or reset the UI state; Task 3 tests the failure path.
