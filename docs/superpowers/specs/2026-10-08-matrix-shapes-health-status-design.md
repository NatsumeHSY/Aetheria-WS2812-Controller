# Matrix Shapes, Session Health, and Connection Status

## Goal

Extend the WS2812 client with a persistent matrix-shape library, recoverable
UDP sessions, periodic device health checks, and a formal connection indicator
in the top bar. Keep the existing dynamic WebView rendering and packet
reliability behavior intact.

## Confirmed scope

- Add a shape area below the matrix editor, occupying the currently unused
  panel space.
- Built-in shapes are read-only and cannot be deleted.
- User-created shapes persist locally and can be loaded, updated, sent, or
  deleted.
- A restarted client must try health recovery before sending a new handshake.
- Health must also detect a device that has gone offline.
- Remove the old bottom status bar and replace it with a top-right connection
  indicator showing state and heartbeat age.

## Matrix-shape design

Built-in shapes are generated by code and exposed together with user shapes.
The initial presets are horizontal line, vertical line, border, checkerboard,
diagonal, and cross. A preset is a monochrome mask: its lit cells are
materialized with the current matrix paint color when loaded or sent.

User shapes store the complete 6x144 color matrix, preserving each selected
color. Empty matrices and malformed dimensions/colors are rejected.

User shapes are stored in `client/configs/matrix_shapes.json`. The file is
created on first save and contains only user data; built-in presets cannot be
modified through the file or bridge API. Each user shape has a stable id,
display name, and matrix.

The WebView shape panel provides:

- a compact preview and `发送` action for every shape;
- `载入` for loading a shape into the editor;
- `保存当前矩阵` for creating a named user shape;
- `更新` and `删除` only for user shapes.

Sending a shape uses the current brightness. Sending a preset uses the current
paint color; sending a user shape uses its stored colors. Shape operations are
handled by a dedicated store in the client layer, while device transmission
continues through `LEDController`.

## Health and session recovery

Add two protocol constants:

```text
HEALTH request:     command 0xFE, empty payload, normal CRC packet
HEALTH_ACK response: LD + 0x03 + expected_seq (two bytes, big endian)
```

The board handles a valid health packet before normal sequence classification:

1. If no session exists, it ignores the request.
2. If the source IP matches the remembered client IP, it updates
   `CLIENT_ADDR` to the new `(ip, port)` and returns the current next expected
   sequence. A `None` expected sequence is reported as `0`.
3. It does not consume a sequence number and does not enqueue an LED command.

The client controller adds `health()` and changes `connect()` to:

1. Send health first.
2. On a valid health acknowledgement, mark connected and resume with the
   returned expected sequence.
3. If health times out, fall back to the existing handshake flow.

Health uses the controller lock, does not advance the application sequence,
and marks the controller disconnected after all retries fail. Existing command
operations can then trigger the normal health-first connect path.

The WebView starts one health check after initial connection and repeats it on a
fixed interval. The interval is owned by the UI script and never overlaps
because controller calls are serialized by the existing lock.

## Formal connection indicator

The old footer text is removed. The top bar receives a dedicated status control
with these states:

- `连接中` — initial connect or recovery is in progress;
- `在线` — the latest health check succeeded;
- `离线` — health retries timed out;
- `错误` — a non-timeout protocol or device error occurred.

The indicator contains a colored state dot, state label, and a heartbeat-age
label such as `心跳 2 秒前`. The age refreshes once per second while the window
is open. It changes to `尚未收到心跳` before the first success and to
`心跳已超时` when offline. The control uses `aria-live="polite"` and visible
focus styling, and its colors remain within the existing dark teal palette.

The status component is independent of the old `.status-bar` footer selectors;
`setStatus` will update this new component so device operations and health
checks share one source of truth.

## Component boundaries

- `client/protocol.py`: health packet and response constants/parsing.
- `client/controller.py`: health-first connect, health polling primitive, and
  sequence restoration.
- `board/main.py`: health request handling and session-port recovery.
- `client/matrix_shapes.py`: preset generation, validation, and JSON-backed
  user-shape CRUD.
- `client/webui/webui.py`: bridge methods for shapes and health.
- `client/webui/scripts/index.js`: shape interactions, health interval, and
  formal status rendering.
- `client/webui/scripts/runtime_const.js`: runtime shape/status markup and
  styling.
- `client/webui/templates/index.html`: matching preview layout and styling.

## Error handling

- Corrupt shape storage is ignored with a safe empty user list; the next save
  rewrites valid JSON.
- Invalid shape names, ids, dimensions, or colors return a structured bridge
  error and do not modify storage.
- Health timeout is treated as offline, not as a protocol exception.
- A failed health recovery falls back to handshake exactly once per connect
  attempt, preserving the existing retry limit.
- Board health packets from a different IP are ignored and cannot replace the
  active session.

## Verification requirements

- Protocol tests cover health packet encoding, response parsing, and sequence
  restoration without sequence advancement.
- Board tests cover health handling for the remembered IP, port replacement,
  unknown IP rejection, and no command enqueue.
- Shape-store tests cover presets, persistence, validation, update, and delete
  permissions.
- WebView bridge tests cover health-first connect and shape CRUD/send routing.
- UI source tests verify the new shape panel, immutable preset controls,
  editable user controls, heartbeat labels, top-bar placement, and removal of
  the bottom status footer.
