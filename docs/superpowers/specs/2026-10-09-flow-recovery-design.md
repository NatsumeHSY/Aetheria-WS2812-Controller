# 流光溢彩、连接恢复与状态同步设计

> 历史设计文档。协议指令分区已由 `docs/superpowers/specs/2026-10-09-command-layout-design.md` supersede；本文中的 FE/FD/FC/FF 指令编号仅保留作为迁移背景，不再代表当前正式协议。

## 目标

修正板端动画生命周期与客户端恢复流程，使客户端能够从维护模式恢复连接并正确同步板端状态，同时将当前错误的单列彩虹扫描改为全矩阵渐变的“流光溢彩”。

## 已确认的命名与约束

- 流光溢彩函数统一命名为 `rainbow`。
- 板端效果方法为 `Effector.rainbow(...)`。
- 客户端控制器方法为 `LEDController.rainbow(...)`。
- 板端协议处理函数为 `led_rainbow(...)`。
- 原有扫描线方法保留为 `scan_line_x(...)`。
- 扫描线新增 `rainbow=False` 参数。
- `0x05` 继续作为流光溢彩指令，现有 8 字节 payload 保持兼容。
- 扫描线不重新暴露为外部控制指令。

## 根因结论

### 连接恢复与同步

维护模式成功后，客户端当前只停止健康检查，没有恢复入口。虽然控制器可以重新创建 UDP Socket，但 UI 没有调用路径。

客户端启动流程只在 `connect()` 返回 `recovered=True` 时调用 `sync()`。维护后板端重新启动通常走 FF 握手，`recovered=False`，因此板端的实际颜色和模式不会进入 UI。

板端静态快照的 RGB 编码本身是正确的；同步缺口主要来自调用条件和过渡动画的未知快照。`led_transition()` 当前将快照标记为不可表示模式 `0xFF`，导致客户端无法还原颜色。

### 动画无法停止

`Effector` 使用共享的 `interrupt_flag`。停止旧线程后，新动画会把同一个标志重置为 `False`；旧线程从睡眠中恢复时可能继续写灯。因此仅设置布尔值无法保证旧线程失效。

### 流光溢彩效果

当前 `rainbow_line_x()` 只点亮一列并移动，实际是彩虹扫描线，不符合“所有 LED 同时点亮、分区颜色渐变”的目标。

## 设计

### 板端动画生命周期

在 `Effector` 内引入动画代次/token：

1. 每次启动或停止效果时递增代次。
2. 新线程捕获自己的代次。
3. 新线程每次写灯前验证代次仍然有效。
4. `stop()` 先令旧代次失效，再执行清理，旧线程即使从 `sleep_ms()` 返回也不能继续写灯。
5. 保留现有 `clear` 参数语义。

代次检查与 NeoPixel 写操作使用同一把轻量锁保护，避免停止动作与一次写帧交错。

### 扫描线与流光溢彩

`scan_line_x(color=COLOR_WHITE, ..., rainbow=False)`：

- `rainbow=False`：使用传入的固定颜色，维持扫描线语义。
- `rainbow=True`：忽略传入颜色，使用现有的单列彩虹扫描行为。
- 只供板端等待连接动画调用，不加入外部 `effect_map`。

`rainbow(start_x=0, end_x=143, brightness=255, interval=500, duration=1, pingpong=False)`：

- 通过横向位置计算每列色相。
- 每一帧为范围内的每一列、每一行写入对应颜色，因此范围内所有 LED 同时点亮。
- 通过色相偏移让渐变持续流动。
- `duration` 控制帧间隔；保留 `interval`/`pingpong` 参数以兼容已有调用和状态保存结构。
- 默认客户端使用全宽范围 `0..143`，因此视觉上是完整 144×6 矩阵的渐变。

协议 `0x05` 的处理函数改为 `led_rainbow()`，仅解析既有 payload 并调用 `EFFECTOR.rainbow(...)`。

### 板端状态同步

- 静态、呼吸、矩阵和流光溢彩继续使用现有 FD 快照协议。
- 过渡动画开始时记录终止 RGB 与亮度作为可恢复稳定状态，不再写入客户端无法识别的 `0xFF` 模式。
- 过渡期间同步以终止颜色为恢复目标；下一次上电或重连后可稳定恢复该颜色。
- 流光溢彩不发送客户端调色板，客户端只同步模式、亮度和节奏。

### 客户端恢复连接

维护模式按钮复用现有顶部操作位：

- 正常状态显示“进入维护模式”。
- 进入维护成功后显示“恢复连接”，保持可点击。
- 点击后调用 Bridge `connect()`，成功后无论是 FE 恢复还是 FF 新握手，都主动调用 `sync()`。
- 同步成功后使用板端状态刷新颜色、模式、亮度、节奏和矩阵；同步失败则保留当前 UI，并显示明确错误。
- 恢复成功后重置按钮为“进入维护模式”，解除维护态并重新启动健康检查。
- 恢复失败时保持“恢复连接”，不启动健康轮询，避免反复自动握手干扰维护操作。

### UI 文案与兼容

- 快捷效果按钮由“彩虹跑马”改为“流光溢彩”。
- Bridge 映射和客户端状态判断统一使用“流光溢彩”。
- 对旧版本地状态中的“彩虹跑马”做兼容迁移，避免旧配置失效。

## 错误处理

- 维护指令仍必须经过正常序号、CRC 和 ACK 流程。
- 恢复连接失败不会清除现有 UI 状态，也不会错误地开启健康轮询。
- FD 同步包损坏、超时或模式无法识别时，保留连接状态并显示同步失败；客户端可以继续使用本地状态。
- 动画线程失效后不得再写入 LED；新效果负责后续显示。

## 验证范围

- 客户端维护模式恢复按钮的状态转换和健康轮询启停。
- FF 新握手后主动 FD 同步，并正确应用板端静态 RGB 颜色。
- 旧“彩虹跑马”状态迁移为“流光溢彩”。
- `scan_line_x(rainbow=False)` 使用传入颜色；`rainbow=True` 忽略传入颜色。
- `rainbow()` 覆盖全部 LED 且生成横向渐变。
- 停止后旧动画线程不能继续写灯。
- `0x05` payload 兼容性、状态快照、完整 Python 测试、MicroPython 源码编译检查和 JavaScript 语法检查。
