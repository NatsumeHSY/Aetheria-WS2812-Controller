# WS2812 音频响应水波效果设计

## 目标

增加“音频响应”效果：Windows 客户端采集系统播放混音并计算频谱摘要，ESP32-C3 接收低维音频数据，在 144×6 WS2812 矩阵上以多个中心点生成向外扩散的水波动画。

成功标准：

- 音频变化能够驱动低频、中频和高频水波；
- 客户端 UI 线程、WebView 和普通控制指令保持响应；
- 网络只传输频谱摘要，不传输完整 864 颗灯的逐帧 RGB；
- 音频丢帧时优先使用最新数据，不让旧帧堆积；
- 客户端退出、设备断线或进入维护模式后，板端不会停留在冻结的音频画面；
- 当前可靠控制协议的 seq、ACK、重发和 0xFFFF -> 0x0000 行为不被实时音频帧破坏；
- 现有静态、矩阵、呼吸、流光溢彩、媒体封面和设备生命周期功能保持兼容。

## 方案选择

### 方案 A：客户端发送完整矩阵帧

不采用。每帧最多需要发送 864 个像素的颜色数据，会增加 UDP 数据量、Python 编码开销和板端接收压力，网络抖动也会直接反映到动画上。

### 方案 B：客户端发送频谱摘要，板端渲染水波

采用。客户端负责 Windows 音频采集和 FFT，板端只维护少量水波状态并计算最终像素。网络负载小，板端效果连续，音频帧丢失时可以由板端自然衰减。

### 方案 C：ESP32 直接采集音频

不采用。当前硬件没有音频输入链路，增加麦克风、采样和模拟前端会扩大硬件与固件范围。

## 总体架构

~~~text
Windows 系统播放混音
        │ WASAPI Loopback
        ▼
client/audio_capture.py
        │ PCM blocks
        ▼
client/audio_spectrum.py
        │ 8 bands + energy + beat
        ▼
client/audio_response.py
        │ 0x0A audio frame
        ▼
board/main.py
        │ latest audio state
        ▼
board/audio_wave.py
        │ 25~30 FPS render
        ▼
board/led_driver.py → WS2812
~~~

音频采集使用系统默认播放设备的 Loopback。Windows WASAPI 支持从 render endpoint 获取当前播放的音频，事件驱动的共享模式适合低延迟采集：

- [Microsoft Loopback Recording](https://learn.microsoft.com/en-gb/windows/win32/coreaudio/loopback-recording)
- [Microsoft Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)

## 客户端音频采集

### AudioCaptureBackend

新增 client/audio_capture.py，定义硬件相关的采集边界。客户端依赖使用 numpy>=2.4,<2.5 和 soundcard>=0.4.4,<0.5；numpy 2.4.4 已在当前虚拟环境中验证可用。

~~~python
class AudioCaptureBackend:
    def start(self) -> None: ...
    def read(self, frame_count: int) -> Sequence[float]: ...
    def stop(self) -> None: ...
    def status(self) -> dict: ...
~~~

首个后端使用 Windows WASAPI Loopback，默认参数为：

- 采样率：48000 Hz；
- 单声道分析，立体声输入先求平均；
- FFT 窗口：1024 samples；
- hop size：512 samples；
- 采集 block：512 samples；
- 音频设备不可用时返回可展示的错误状态，不使客户端进程退出。

采集线程使用有界队列，最多保留两个未处理 block。队列满时丢弃最旧 block，保证分析结果跟随当前声音。

## 频谱分析

新增 client/audio_spectrum.py，只包含可在主机上测试的纯计算逻辑。

### 输出模型

~~~python
AudioFrame(
    frame_seq: int,
    bands: tuple[int, int, int, int, int, int, int, int],
    energy: int,
    beat: int,
)
~~~

字段范围：

- frame_seq：0~65535，独立于可靠控制指令的 seq；
- bands：8 个 0~255 的对数频段能量；
- energy：整体能量 0~255；
- beat：低频突增触发值 0~255。

频段覆盖约 60 Hz～8 kHz，使用对数分布。分析过程包括 Hann 窗、幅值计算、每频段聚合、噪声门限、自动增益和攻击/释放平滑。

建议的初始平滑参数：

- 攻击时间约 20 ms；
- 释放时间约 120 ms；
- 低频突增超过自适应基线后生成 beat 值；
- 对外发布频率限制为 30 FPS，内部 FFT 可以按 hop size 更高频率运行。

## 板端水波引擎

新增 board/audio_wave.py，不让音频包处理线程直接执行完整矩阵渲染。

### 中心点

使用固定、确定性的中心点集合，初版为：

~~~text
(18, 1), (48, 4), (72, 2), (96, 4), (126, 1)
~~~

固定中心点避免每个音频包携带坐标，也避免随机动画造成不可复现的视觉跳变。

### 频段映射

- 低频频段：驱动左侧和右侧的大半径水波；
- 中频频段：驱动中部和两侧的中等半径水波；
- 高频频段：驱动较小半径、较快衰减的细波纹；
- beat：对当前活跃中心进行瞬时强度注入。

每个中心维护：

~~~text
radius
amplitude
decay
band_level
trigger_level
~~~

矩阵始终先以快捷颜色列表中的第一个颜色作为常量底色。音频帧不会直接把整块矩阵刷黑，也不会因为持续高电平而每帧重置波纹。每个中心只在对应频段、整体能量或 beat 从低于阈值上升时生成一次“水滴”事件：半径从 0 开始，注入一次波纹强度，然后逐帧向外推进并衰减。只有当信号重新回落后再次上升，或出现足够明显的能量上升沿时，才会再次触发水滴。

每一帧先推进已有波纹的半径和衰减，再计算每个 LED 到中心点的距离。距离接近当前半径时形成暗环，按波纹强度降低该 LED 的当前亮度；距离偏离时按环宽衰减。颜色始终保持常量底色，不叠加额外颜色。这样静音时仍保持底色，音频冲击表现为“水滴落入并以一圈较暗的亮度向四周扩散”。

基础颜色来自客户端快捷颜色列表。只有一个颜色时所有中心使用该颜色；有多个颜色时中心按列表循环取色。颜色保持逻辑 RGB，最终仍由板端 LedDriver 统一应用白平衡和全局亮度。

### 刷新节奏

WS2812 发送 864 颗灯的理论传输时间约为 26 ms，因此板端目标为 25～30 FPS。A1 全局节奏参数用于水波传播速度和衰减速度，A0 全局亮度继续由输出层使用。

板端使用预计算距离表或整数距离近似，避免每帧创建大量临时 tuple 和浮点对象。音频状态只保留最新一帧；只要仍能收到静音频谱帧，板端就继续保持底色。超过约 200 ms 完全没有新数据时，才由 watchdog 认定音频链路失活，停止音频模式并清空输出或恢复安全静态状态。

## 协议设计

### 指令分配

当前 F0 为握手，F1~F5 已分别用于健康检查、同步、维护、重启和重置。00~09 已用于现有效果，音频响应使用下一个效果指令 `0x0A`：

~~~text
0x0A + 0x00 AUDIO_START
0x0A + 0x01 AUDIO_FRAME
0x0A + 0x02 AUDIO_STOP
~~~

F6 及之后继续保留给未来系统指令扩展。

### 0x0A/0x00：启动/配置

这是效果指令中的可靠子类型，使用现有包头、CRC、全局 seq、ACK 和重发机制。

payload：

~~~text
format_version:u8
color_count:u8
color_0:R,G,B
color_1:R,G,B
...
~~~

颜色数量范围为 1~8。板端收到后停止旧效果，初始化水波状态，并启动音频渲染循环。

### 0x0A/0x01：实时音频帧

实时音频帧仍然使用 `0x0A` 作为命令字，并在 payload 第一个字节放置子类型 `0x01`。它使用当前包头和 CRC，但不进入可靠控制的 EXPECTED_SEQ 窗口，也不返回 ACK。payload 固定为：

~~~text
subtype:u8 = 0x01
audio_seq:u16
energy:u8
beat:u8
band_0:u8
band_1:u8
...
band_7:u8
~~~

包头中的可靠 seq 固定为 0，客户端不会因此推进普通控制指令序号。板端为 `0x0A/0x01` 维护独立的 audio_seq，只接受更新的音频帧，丢包、乱序和重复帧直接丢弃。

客户端发送线程只保留最新待发送帧，不等待 ACK，不进行重发。实时音频帧发送异常由独立音频状态上报，普通健康检查仍负责判断设备连接状态。

### 0x0A/0x02：停止

这是效果指令中的可靠子类型。收到后停止音频渲染，恢复安全静态状态或清空当前输出，并通过现有 ACK 返回结果。

## 客户端控制层

client/controller.py 增加：

~~~python
start_audio(colors: Sequence[Sequence[int]]) -> int
send_audio_frame(frame: AudioFrame) -> None
stop_audio() -> int
~~~

client/audio_response.py 负责：

- 启动/停止采集线程；
- 启动/停止频谱分析；
- 管理最新频谱帧；
- 调用 LEDController.start_audio() 和 send_audio_frame()；
- 暴露音频设备、采集、发送和最近帧时间状态；
- 在断开连接、进入维护模式、重启和重置时停止音频发送。

## UI 和状态同步

### 模式

在现有效果模式中加入：

~~~text
音频响应
~~~

当前节奏滑块继续可用，用于板端水波速度和衰减。亮度、白平衡和快捷颜色沿用现有控制。

音频模式状态区显示：

- 音频设备是否可用；
- 是否检测到播放信号；
- 低频、中频、高频能量；
- 最近一帧发送时间；
- 当前板端连接状态。

生产 UI 继续由 runtime_const.js 动态生成，templates/index.html 只同步预览结构和样式。

### 生命周期

- 进入音频模式：发送 `0x0A/0x00`，随后启动 `0x0A/0x01` 实时帧；
- 切换到其它模式：发送 `0x0A/0x02`，停止音频线程，再应用新模式；
- 进入维护模式：停止音频线程后发送维护指令；
- 客户端关闭：保存当前 UI 模式和颜色列表，停止音频线程；
- 下次启动：完成 health/sync 后，如果本地状态是音频模式，重新发送 `0x0A/0x00` 并恢复实时发送；
- 板端断线：停止实时音频帧发送，等待重连后重新执行 `0x0A/0x00`；
- 板端重启或断电：不把“音频正在运行”作为板端持久化模式，客户端重新连接后恢复。

## 错误处理

- 没有默认播放设备、Loopback 不可用或权限异常：音频模式进入“不可用”状态，不影响静态控制；
- 音频捕获线程异常：停止实时音频帧发送，保留设备健康检查，UI 显示错误；
- `0x0A/0x00` 或 `0x0A/0x02` 没有 ACK：沿用现有重连和错误提示；
- 实时音频帧丢包：板端继续使用上一帧并自然衰减，不触发普通控制重发；
- 实时音频帧长时间无数据：板端 watchdog 退出音频效果，避免冻结画面；
- 切换模式时旧音频线程必须先退出，防止旧帧覆盖新模式。

## 持久化与同步边界

音频响应属于客户端驱动模式：

- 客户端保存音频模式、快捷颜色和节奏参数；
- 板端不把“音频实时状态”写入 state.bin；
- 板端断电后恢复最后一个可独立运行的普通状态；
- 客户端完成 health/sync 后再重新启动音频模式；
- sync 不返回完整音频频谱，只返回普通板端状态和白平衡。

## 测试范围

### 纯逻辑测试

- FFT 输入长度不足、静音、单频、混合频率和满幅输入；
- 8 频段范围、平滑、噪声门限和 beat 检测；
- 音频序号回绕、重复帧、乱序帧和丢帧；
- `0x0A/0x00`、`0x0A/0x01`、`0x0A/0x02` payload 长度、范围和 CRC；
- 水波半径推进、衰减、多中心叠加、颜色循环和亮度限制；
- 超时 watchdog 退出和模式切换时的 generation/stop 行为。

### 客户端集成测试

- 音频模式启动和停止；
- 实时帧不推进普通控制 seq；
- 音频发送不阻塞 health/sync/普通控制；
- 采集设备异常不会让 WebView 退出；
- disconnect、maintenance、restart、reset 会停止音频线程；
- 本地 UI 状态恢复后重新发送 `0x0A/0x00`。

### 硬件验收

- 静音时矩阵逐渐归零；
- 低频鼓点触发大范围波纹；
- 高频声音产生细小快速波纹；
- 连续音乐播放时无明显冻结、旧帧拖尾或模式抢占；
- 普通灯效和音频模式切换后输出不再被旧音频帧覆盖。

## 范围外内容

- 不在本次功能中加入麦克风输入；
- 不在本次功能中加入完整 FFT 可视化编辑器；
- 不改变现有 A0、A1、A2 参数协议；
- 不占用 F 段新增系统指令；
- 不将完整 864 像素帧加入 UDP 协议；
- 不把音频实时状态写入板端持久化文件。
